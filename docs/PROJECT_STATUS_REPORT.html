1. How to read this report

Every feature/module is classified into one of four states:

  • COMPLETED — Built and wired end-to-end (UI + service + backend call), usable.
  • PARTIAL — Works but with gaps: missing sub-cases, commented-out pieces, or rough edges.
  • INCOMPLETE — Started (some code exists) but not usable / not reachable in the app.
  • UNTOUCHED — Not started, placeholder, or an abandoned dependency with no working code.

Note: "usable" assumes the app is pointed at a running API (see the connectivity setup in docs/ONBOARDING.md). Backend endpoint correctness is out of scope for this client-side review.

The app's core patient journey is functionally complete: launch → browse doctors → book appointment → log in → view profile, appointments, discharge history, and download/share PDF reports. Authentication (login, forgot-password via OTP, logout) is implemented end-to-end.

The main weaknesses are (a) security & session robustness (no token/JWT auth; login state is largely in-memory), (b) a few half-finished features (bill categories has backend code but no screen; guest-appointment display is commented out; some report categories are disabled), and (c) abandoned scaffolding (Firebase/Google-Sign-In dependencies with no code, several fully-commented legacy files, and the default test still present and broken).

Overall maturity: A working demo/MVP-grade app. It can be shown and used on a LAN against the dev API. It is not yet production-hardened (security, session persistence, error handling consistency, tests, and cleanup remain).

4. Module-by-module detail

4.1 Authentication & session

Completed: phone+password login, OTP-based forgot-password (verify phone → send OTP → verify → set new password), and logout with confirmation.

Gaps: the real auth code sits inside login_screen.dart rather than a dedicated service; the separate auth_service.dart is legacy and fully commented. Login state is not persisted (in-memory), so users are logged out on every app restart even though logout clears preferences. There is no token/JWT — subsequent API calls identify the patient by MR number in the URL.

4.2 Appointments

Completed: browsing doctors (paginated + filter), viewing a doctor's schedule, booking for self/relative/guest, and viewing current vs past appointments. Booking for logged-in users writes to the server; guest bookings write to the server and local SQLite.

Gaps: the guest's locally-saved appointments are never displayed back (the read path in AppointmentsInfoScreen is commented out). Some success dialogs/snackbars are commented. A hardcoded phone-verify URL (172.16.40.10:8080) bypasses the central config.

4.3 Reports (PDF)

Completed: report history list, on-device PDF generation/download, in-app viewing (Syncfusion), and sharing (share_plus); discharge report generation.

Gaps: in reports_screen.dart, direct per-category fetches (lab/gastro/radiology/prescription) are commented out; the screen leans on the generic generate endpoint. Some "share coming soon" remnants remain.

4.4 Profile & discharge

Completed: patient profile from latest visit; paginated discharge history; discharge report PDF. Solid loading/error states in these screens.

4.5 Billing

Incomplete: the service and model are written (and even handle a self-signed cert), but there is no UI screen and no navigation entry, so the feature can't be used. It also points at a separate hardcoded server.

6. Technical debt & risks (prioritized)

Security (high): No token/JWT auth; patient data is fetched using the MR number in the URL with no authorization header, so any client that knows/guesses an MR number could pull records directly from the API. The backend also ships plaintext DB credentials in appsettings.json. These should be addressed before any production/public release.
  • HIGH Auth tokens: introduce JWT/bearer auth end-to-end (API + app).
  • HIGH Config & secrets: stop committing credentials; use environment/secret storage; rotate the exposed DB password.
  • MED Hardcoded IPs bypassing ApiConfig.baseUrl in bill_category_service.dart (172.16.40.56) and doctor_schedule_screen.dart (172.16.40.10). Unify to one config.
  • MED Session persistence: save login to SharedPreferences and restore on splash; make logout/login symmetric.
  • MED Context-after-await warnings (potential crashes) across several screens — add if (!mounted) return; guards.
  • LOW Cleanup: remove dead files & unused dependencies (Firebase/Google if not planned); fix print() usage; fix naming lints.
  • LOW Tests: add at least smoke tests for services/models; fix the broken default test.
